# v0.10.0 – Volume normalization

## Intent

Songs from different sources (own files, YouTube, SoundCloud, long DJ mixes)
should play at a similar loudness, so the user does not reach for the volume
between songs. Nothing specific annoyed the user; it is a wish from the
2026-11-24 list ("volume normalisation, ReplayGain-style loudness measured at
import"). So it stays small and invisible: one switch, no tuning.

## Goals

- Every song in the library gets one measured loudness value (EBU R128
  integrated loudness, LUFS), measured once, by owntune itself, from the
  decoded audio.
- With the switch on, playback lowers each song to a common target level.
- Existing libraries are measured too, in the background, without the user
  doing anything.

## Non-goals

- No boosting of quiet songs (see Constraints). Quiet songs play unchanged.
- No album mode (keeping the level differences inside an album). Track mode
  only.
- No "Loud / Normal / Quiet" choice like Spotify, no target slider.
- No limiter / compressor, no true-peak handling (we only ever attenuate,
  so nothing can clip).
- Reading or writing ReplayGain tags. owntune neither uses existing
  ReplayGain tags nor writes its measurement into the files; the value
  lives in the database only.
- No UI that shows the measured loudness or the measuring progress.

## Anti-goals (would make it a failure even if it works)

- Import or download gets slower or can fail because of the measurement.
- Playback stutters, starts late, or a song starts loud and then drops in
  volume.
- The measurement drains the battery noticeably or makes the app feel slow
  (e.g. measuring many songs in parallel on the iPhone).
- A file that cannot be decoded for measuring is re-decoded on every start.
- Measuring in the background on iOS gets the app killed and stops the
  music.

## Constraints

- just_audio's volume is 0.0–1.0 on iOS; it cannot amplify. Normalization is
  therefore attenuation only.
- Development without a Mac; the iPhone is the real target. Decoding speed
  and memory must be fine on the phone; long DJ mixes (1–2 h) exist in the
  library.
- Rust is the place for file-format work (lofty already lives there). New
  crates go into `rust/Cargo.toml` with exact versions, like the others.
- Formats in the library: MP3, M4A/AAC (also ALAC possible in `.m4a`), FLAC,
  WAV, plus the downloads: YouTube itag 140 (DASH-fragmented MP4, AAC-LC) and
  SoundCloud (HLS segments joined into one fragmented MP4, AAC-LC, with the
  patched `mvhd`). Fixtures for all of them exist in `test/fixtures/audio`
  (`tagged.*`, `demo_3.wav`, `dash.m4a`, `hls_*`).
- Everything testable on Linux; Rust calls injected as functions (like
  `Importer(read:)`), so widget/unit tests run without the native library.

## Approaches considered

- **A – measure every file ourselves (picked by the user).** Rust decodes the
  audio (`symphonia`) and measures it (`ebur128`). One method for every
  source, so the values are comparable. Costs: new Rust dependencies (app
  ~1–2 MB larger), ~1–2 s of CPU per 4-minute song, a one-time background
  pass over the existing library.
- B – use existing values only (ReplayGain tags, YouTube's `loudnessDb`).
  Little code, but patchy: SoundCloud and untagged files stay unnormalized,
  and ReplayGain and YouTube use different reference levels.
- C – hybrid of A and B. All the cost of A plus the inconsistency of B.

## Design

### Measuring (Rust)

- New function in `rust/src/api/` (e.g. `measure_loudness(path) ->
  LoudnessResult`), async (not `#[frb(sync)]`), so it runs on FRB's worker
  thread and never on the UI thread.
- Decodes the whole file with `symphonia` (features for mp3, aac, isomp4,
  flac, wav/pcm, alac) and feeds the samples to `ebur128` in integrated mode,
  streaming (never the whole file in memory).
- Returns the integrated loudness in LUFS, or a failure with a message
  (undecodable, unsupported codec, silent file: integrated loudness of
  silence is -inf and counts as a failure).
- Must work on the DASH and HLS fragmented MP4s. **This is the main risk:
  the first plan task proves symphonia decodes `dash.m4a` and the `hls_*`
  fixture joined like a download** before anything else is built.
  **Downloads must be normalized in v0.10.0 (decided by the user).** If
  symphonia's MP4 reader cannot read them, the fallback is a small own
  fragmented-MP4 reader in Rust (walk `moov`/`moof`/`trun`/`mdat`, take the
  AAC config from `esds`) that hands the AAC packets to symphonia's AAC
  decoder. Not allowed as a fallback: the platform decoders (AVFoundation,
  MediaCodec), because they break "testable on Linux"; and shipping with
  downloads unnormalized.

### Storage

- Schema v5: `tracks.loudness_lufs` (REAL, nullable; null = not measured
  yet) and `tracks.loudness_attempt` (INTEGER, nullable: the measurer
  version that last tried this row and failed; null = never failed).
  *My call (after the builder check):* a version instead of a boolean, so a
  later release with a better decoder bumps `kLoudnessMeasurerVersion` and
  re-measures only the rows that failed before. A stored value stays valid
  forever: a file's audio never changes after import (Edit Info only
  rewrites tags and covers).

### The background measurer

- One measurer for everything: it picks tracks with `loudness_lufs IS NULL
  AND (loudness_attempt IS NULL OR loudness_attempt <
  kLoudnessMeasurerVersion)`, *my call:* newest first (by `added_at`), so a
  fresh import or download is normalized soon, and measures **one at a
  time**, writing the result (or `loudness_attempt` on failure) after each
  song.
- Runs after startup and whenever new tracks appear (import, download),
  **only while the app is in the foreground**. *My call (after the builder
  check):* the app usually runs in the background with music playing, and
  iOS may kill a background app that keeps the CPU busy, which would stop
  playback. When the app goes to the background, the current measurement is
  cancelled within a few seconds (the Rust side checks a cancel flag while
  decoding) and redone from the start when the app is back; nothing is
  stored for a cancelled song. Downloads and imports happen in the
  foreground anyway, so new songs are still measured soon. The
  Importer and DownloadController do not wait for it and do not change;
  import speed and failures stay exactly as today.
- Runs regardless of the switch, so turning the switch on later works at
  once. *My call.*
- A deleted track is skipped (row gone; its result is dropped). Errors are
  swallowed and recorded as `loudness_attempt`; the measurer never throws
  into the app.
- No UI and no notification while it runs.

### Playback

- `AudioEngine` gets `setVolume(double)` (just_audio `setVolume`; the Linux
  media_kit backend supports it too); `FakeAudioEngine` records it.
- Target level: **−14 LUFS** (Spotify "Normal"). Gain for a song:
  `volume = min(1.0, 10^((−14 − loudness) / 20))`. Not measured yet, failed,
  or switch off → `1.0`.
- The controller sets the volume for an entry **before** it starts playing
  it (on load), so a song never starts at the wrong level. When the switch
  changes, the current song's volume follows at once. When a measurement
  for the current song arrives mid-song, *my call:* keep the volume until
  the next load (no audible jump mid-song).
- Effect to expect: with the switch on, most modern songs (−8…−11 LUFS) get
  3–6 dB quieter; the user turns the phone volume up once.

### Settings

- New group **Playback** in the settings sheet with a switch **Normalize
  Volume**, footnote "Plays all songs at a similar loudness." Default **on**.
  Stored in `settings_entries` like the other settings (`AppSettings`).
