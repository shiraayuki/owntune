# M0: Skeleton – Design

Date: 2026-11-18 · Overall plan: see `CLAUDE.md`

## Intent

M0 proves that the whole chain works before there are any features: write code on a Linux laptop without a Mac → build for iOS in the cloud → sideload and launch on the iPhone. Because iOS can neither be built nor tested locally, this chain is the biggest risk of the project. It should be settled while the app is still empty and failures are easy to locate.

Rust (flutter_rust_bridge + `lofty`) is added in M0 already. Reason: writing tags reliably (M3) practically requires Rust anyway, and building Rust for iOS in CI is the most failure-prone part of the chain.

## Goals

- Flutter project `owntune` with the platforms iOS, Android, and Linux.
- Rust core in `rust/`, bound via flutter_rust_bridge v2, including a simple call whose result is visible in the app.
- Public GitHub repo with Actions workflows:
  - **Linux job** (on every push/PR): `flutter analyze`, `flutter test`, `cargo test` and `cargo clippy` for the Rust core, build an Android APK.
  - **macOS job** (only on version tags `v*` and manually — changed on 2026-11-18 because waiting for macOS runners slows down daily development; daily work happens on Linux or in the Android emulator): `flutter build ios --release --no-codesign`, package an unsigned `.ipa` from it (`Payload/Runner.app` → zip), and upload it as an artifact.
- Local development environment on the laptop: Flutter, Rust (rustup), CMake, and Ninja, so that `flutter run -d linux` works.
- Update `CLAUDE.md` to the actual state (commands, folders, codegen steps).

**Done when:** The empty app starts on Linux and shows the result of the Rust call, and the same app, installed from the CI `.ipa` via SideStore/iloader, starts on the iPhone and shows the same result.

## Non-goals

- No features from M1+ (no import, no database, no audio). drift, Riverpod, just_audio etc. are added only with the milestone that needs them.
- No local Android SDK and no emulator in M0; Android is only built in CI. Local emulator setup comes later.
- No signing, no TestFlight, no store publishing.

## Anti-goals

- A CI that is "green" but whose `.ipa` does not start on the iPhone or cannot execute the Rust call. Success is measured on the real device, not by CI status.
- Platform-specific workarounds that only work on one target. The Rust call must run on Linux, Android (build), and iOS through the same Dart code.

## Constraints

- Development machine: Arch-based Linux (Omarchy), no Mac. Available: git, GitHub CLI (logged in), clang, GTK3, libmpv. Missing: Flutter, Rust, CMake, Ninja, Java, Android SDK.
- Public repo → GitHub Actions minutes (incl. macOS) are free.
- Installation on the iPhone is done manually by the user via SideStore/iloader with a free Apple ID.

## Approaches

**When to add Rust** (decided by the user: A)
- **A – Rust in M0:** more complex CI, but the risk "Rust on iOS via the cloud" is settled while the app is empty. **Chosen.**
- B – Rust later: faster M0, but the biggest risk moves into M1/M3, in the middle of feature code.

**Rust binding** (my call)
- **flutter_rust_bridge v2 with its standard build integration (cargokit):** Rust is built automatically for each platform during `flutter build`; no separate build step for prebuilt libraries. **Chosen.**
- Prebuilt Rust libraries per platform, produced separately by CI and linked in: more control, but much more custom build code. Not worth it without need.

**Repo visibility** (decided by the user: public)
- **Public:** no minute costs. **Chosen.**
- Private: code stays private, but only about 200 effective macOS minutes per month on the free tier.

## Decisions

By the user:
- Rust core already in M0.
- Public GitHub repo, workflows via GitHub Actions.

My calls (not objected to by the user):
- flutter_rust_bridge v2 with standard integration; Rust crate in `rust/`.
- The Android platform is created and only built in CI (APK), no local Android SDK.
- Provisional bundle ID / application ID: `dev.owntune.app`.
- The repo is named `owntune`, lives under the logged-in GitHub account, main branch `main`.
- Tools are installed only after this design is approved.

Settled by me while writing it up:
- The Rust core already depends on `lofty`, and the test call uses it (e.g. returns the list of formats lofty supports). This proves not just "Rust on iOS" but exactly the library needed later, on all targets.
- Code generated by flutter_rust_bridge (Dart and Rust) is committed. CI checks that it matches the current Rust code, so it does not need codegen as a mandatory step before every build.
- The M0 UI is a single screen with the app name and the result of the Rust call; nothing more.

## Left to the implementer

- How to install Flutter on Arch (official git checkout, AUR package, or fvm); stable channel and reproducible is what matters.
- Concrete versions of Flutter, flutter_rust_bridge, `lofty`, and the Actions; pick current stable versions and pin them.
- iOS minimum version: Flutter default unless there is a reason against it.
- CI caching (Flutter SDK, Cargo, Pods), as long as the workflows stay correct.
- Whether and how a Dart test checks the Rust call on the Linux runner against the real native library; at minimum one Rust unit test for the core function and one widget test for the home screen.
