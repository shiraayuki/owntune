# M2 v0.4.1 — Background playback, system controls, restore (design)

**Size:** project. Completes M2. *Done when:* plays on the iPhone with the screen locked and can be controlled there. The user approved the approach in chat and asked to go straight to implementation without reviewing this document.

## Intent

v0.4.0 plays only while the app is open. v0.4.1 keeps music going with the screen locked or another app in front, puts the song and its controls on the lock screen / Control Center (Android: the media notification), and brings the player back after a restart.

## Goals

- **Background playback:** `UIBackgroundModes: audio` (iOS), audio_service foreground service (Android). The `audio_session` music category from v0.4.0 stays.
- **System controls** via audio_service: title, artist, album, duration and cover (file URI of the stored cover); play, pause, next, previous, seek. Previous follows the in-app rule (restart after 3 s). Next is offered only when the queue has one.
- **System pauses are reflected:** when the OS pauses playback (phone call, other app takes audio focus, headphones unplugged), the in-app play state follows; after a transient interruption ends, just_audio may resume, and the UI follows too.
- **Restore after restart:** queue (track ids), current index, source label, repeat mode and position are saved; on the next start the player comes back **paused at the saved position** (user's choice). Songs deleted meanwhile are dropped like any deletion; if none remain, nothing is restored.
- **Saving:** on every queue/index/repeat change, on pause, on seek, and every 5 s while playing. Losing the last few seconds after a kill is accepted.
- Failures stay visible: audio_service setup is part of `startUp()` (→ `StartupFailed`); a broken saved state is ignored (player starts empty), never a startup failure.

## Non-goals

Shuffle; gapless; Android Auto / CarPlay browsing; a queue shown in the system UI; Linux MPRIS (audio_service is a no-op on Linux; Linux stays a dev target).

## Approaches

1. **audio_service as a thin layer in front of `PlayerController`** (chosen): a `BaseAudioHandler` forwards system commands to the controller and publishes `mediaItem` / `playbackState` from it. The queue logic stays in Dart and testable.
2. `just_audio_background`: needs the queue inside the plugin; undoes v0.4.0's design. Rejected.
3. Own Swift bridge to MPRemoteCommandCenter: native code that cannot be built or debugged without a Mac. Rejected.

Storage: one JSON entry in the existing `settings_entries` table (key `player.state`), no schema migration. A dedicated table would need a migration for a single row.

## Decided by the builder (my calls)

- `AudioEngine` gains `Stream<bool> get playingChanges`; the controller adopts the engine's play state when it changes on its own.
- System controls sit behind a small `SystemControls` interface (`NoSystemControls` for Linux/tests, `AudioServiceControls` for phones), so widget tests stay platform-free.
- The system position is published with `updatePosition` on play/pause, track change and seeks (a position jump > 2 s against the expected position counts as a seek); the OS extrapolates in between.
- Android: `MainActivity` extends `AudioServiceActivity`; manifest gets WAKE_LOCK, FOREGROUND_SERVICE, FOREGROUND_SERVICE_MEDIA_PLAYBACK, the service and the media button receiver. `androidStopForegroundOnPause: true` (default best practice).
- Restore happens when the first library snapshot arrives; nothing plays by itself.

## Left to the builder

File layout under `lib/player/`, JSON field names, test split. Manual iPhone checklist in the plan's last task: lock screen shows song and cover, controls work, scrubbing works, playback survives locking and app switching, a phone call pauses, restart restores paused at the position.
