# v0.6.1 – Covers, multi-select and text tabs

Date: 2026-11-21 · Status: draft

## Intent

One release with three parts the user picked together:

1. **Text tabs** replace the iOS segmented control as the view switch. The
   user finds the segmented look dated and picked variant B of
   `docs/mockups/switch-v1/` ("more modern", YouTube Music style).
2. **Covers** (the rest of M3): pick a cover from Photos or Files, crop it
   square, or remove it, for one song or for all songs of an album/artist,
   written into the files on Save.
3. **Multi-select in Songs** (the rest of M3): select several songs, then
   Edit Info or Delete them together.

Plus the deferred small fixes from v0.6.0 (below).

Naming: this was "v0.5.1" in the roadmap; since v0.6.0 is out it ships as
**v0.6.1**, and SoundCloud moves to **v0.6.2** (my call). Update CLAUDE.md's
status and milestone lines accordingly.

## Goals

- Library sub-tabs (Songs | Albums | Artists) and Search Online
  (Songs | Videos) use text tabs.
- Edit Info shows the cover and lets the user replace or remove it; in bulk
  too (decided by the user: an album gets one cover for all its songs at once).
- Songs can be multi-selected for bulk Edit Info and Delete.

## Non-goals

- Add to Playlist (M4) – shown disabled in the selection bar, as in mockup 04.
- Multi-select in Albums, Artists, album/artist pages or Search.
- Swiping between tabs (tap only).
- Finding covers online, cover thumbnails, a separate album cover that is not
  in the song files.
- Changing the Appearance switch in Settings: it stays `Segmented` (it is a
  setting, not a view switch – my call; the user did not discuss it).

## Anti-goals

- Database and files drifting apart: a song's `coverFile` must only change
  when its file was written successfully (same rule as the tags in v0.5.0).
- Breaking duplicate detection: `contentHash` and `fileName` keep their import
  values after a cover edit (as for tags).
- Bloating files: a 12 MP photo must not be embedded as-is.
- Anything that only works on the iPhone and cannot be tested on Linux,
  except the thin picker call.

## Constraints

- Linux is the daily target; the logic (crop math, image processing, save
  rules, selection) must be testable there without the native library.
- Add only packages the release needs. The chosen approach needs none.
- Imports: `material_ui` / `cupertino_ui`, not `flutter/material.dart` /
  `cupertino.dart`.
- Changes in `rust/src/api/` require `flutter_rust_bridge_codegen generate`;
  generated code is committed.
- Covers are stored once under `covers/<blake3-of-image>.<ext>` via
  `covers/<random>.part`, file names only in the DB.

## Approaches (picked: 1)

1. **No new packages (picked).** Picking via the existing `file_picker`:
   `FileType.image` opens the photo library on iOS ("Choose from Photos"),
   the default type opens the Files app ("Choose File"). Cropping is an own
   full-screen page with `InteractiveViewer` over a square frame; the crop
   rectangle is turned into the final image in Dart. Matches the mockups
   exactly, the math is testable on Linux; cost: we write the gesture/crop
   math ourselves.
2. **Packages `image_picker` + `crop_your_image`.** Gestures come ready-made,
   but two packages more, harder to match the mockups, and `image_picker` is
   weak on Linux (the daily target).
3. **Native cropper (`image_cropper`).** Dropped: iPhone-only, not testable
   on Linux.

## Design

### 1 · Text tabs

Spec: `docs/mockups/switch-v1/b1-library-tabs.html`,
`b2-online-tabs.html` and `switch.css` (`.utabs`).

- New widget `TextTabs<T>` (e.g. `lib/app/text_tabs.dart`), same API shape as
  `Segmented<T>` (`segments`, `value`, `onChanged`).
- Look: labels left-aligned in a row, 24pt gap, 16pt side padding; 17pt,
  weight ~650 (use `FontWeight.w600`/`w700` as fits the font); unselected in
  `muted`, selected in `text`; under the selected label a 3pt accent bar with
  rounded ends, as wide as the label; a 0.5pt hairline (`line`) across the
  row (16pt in from both sides) under the bars. Labels have ~4pt above and
  ~10pt below; 12pt gap to the search field below.
- Semantics like `Segmented` (button, selected). Whether the bar slides
  between labels or just jumps is left to the builder.
- Used in `LibraryTab` (replacing the `library-segments` padding block, still
  hidden while the library is empty) and in `SearchOnlineScreen` (Songs |
  Videos). `Segmented` stays for Settings only.
- Update widget tests that find the segmented control; `segmented_test.dart`
  stays.

### 2 · Covers in Edit Info

Spec: `docs/mockups/roadmap-v1/01-edit-cover.html`, `02-cover-menu.html`,
`03-cover-crop.html` (+ `roadmap.css` `.cover-edit`).

**Cover block** at the top of Edit Info, above the first field group, for one
song and in bulk: a 150pt square with 12pt corners and a soft shadow,
centered; below it an "Edit Cover" pill (photo icon, accent text, `fill`
background). The square shows:

- the pending new cover, if one was picked;
- the empty placeholder (as `Artwork` shows songs without cover) if the
  cover is pending removal, or if no song has a cover;
- in bulk, the common cover if all songs share the same `coverFile`;
- in bulk with differing covers (incl. some without): a placeholder with the
  label "Mixed", consistent with the "Mixed" text fields.

**Cover menu** (tapping "Edit Cover" or the square): an action sheet in the
app's existing sheet/menu style with the heading "Cover for “<title>”" (one
song) or "Cover for <n> songs" (bulk), and the rows "Choose from Photos",
"Choose File", "Remove Cover" (red; only when at least one song has a cover
or a new one is pending), "Cancel".

**Picking:** `file_picker` with `FileType.image` (Photos) or the default type
with image extensions (`jpg`, `jpeg`, `png`, `webp`, plus `heic`/`heif` so
they can be picked and get the clear error below) for Files; one file, bytes
loaded. On Linux both rows open the file dialog. The
picker sits behind a small interface/provider (like `audio_file_picker.dart`)
so widget tests fake it. Cancelling the picker changes nothing.

**Crop page** (full screen, pushed over Edit Info): top row "Cancel" ·
"Move and Scale" · "Choose"; a square frame (screen width minus margins)
with the area outside it dimmed; hint "Pinch to zoom · drag to move" below.
The image starts scaled so it just covers the square, centered; pinch zooms
in (min scale = covers the square, max e.g. 5× – builder's call), drag moves;
the image can never leave a gap inside the frame. "Choose" turns the visible
square into a rectangle in source-image pixels and returns it; "Cancel"
returns to Edit Info with nothing changed. Always shown after picking, even
for square images.

**Making the cover** (pure, testable): source bytes + crop rectangle →
JPEG (quality 90), cropped, downscaled so the side is at most 1000 px (never
upscaled). EXIF orientation must be applied before cropping, since the crop
page shows the image upright. Decoding and encoding with the `image`
package, the CPU part in an isolate.

**HEIC (decided by the user: option "no conversion").** iPhone photos are
often HEIC, which neither the `image` package nor (probably) Flutter's iOS
image codecs can read. "Choose from Photos" therefore asks `file_picker` to
hand over JPEG (its image compression option on iOS, which transcodes Photos
picks); so the normal path works with HEIC photos. A HEIC/HEIF (or any other
unreadable) file picked via "Choose File" shows an error dialog – "This image
can't be read. Choose a JPEG or PNG." – and changes nothing; HEIC from Files
is an accepted gap. No conversion package, no Swift code. **Verify early:**
trigger an iOS build (`gh workflow run iOS`) as soon as picking works and let
the user pick a HEIC photo from Photos on the iPhone, before building the
rest on it. If Photos does not deliver JPEG, stop and bring it back to the
user.

**Pending state:** the cover change is part of the edit – `keep` (default),
`set(bytes, mime)` or `remove` – next to the field changes in `TagEdit`
(exact shape is the builder's call). Save is enabled when fields or the cover
changed. Nothing is written before Save; Cancel discards it.

**Saving** (`TagSaver`, same rule as tags: file first, row only on success):

- A song is skipped when neither its tags nor its cover change (remove on a
  song without cover = no change).
- `set`: the same cover bytes are written into every song's file together
  with its tags in one `write_tags` call. Before the rows are updated, the
  image is stored once as `covers/<blake3>.jpg` (via `covers/<random>.part`,
  skipped if it exists). The rows of all songs whose file was written get
  that `coverFile`, in the same transaction as their tags.
- `remove`: all pictures are removed from the file; `coverFile` becomes null.
- Afterwards, old cover files no longer referenced by any row are deleted
  (best effort; `cleanupOrphans()` at startup catches leftovers). If no file
  was written, the newly stored cover file is deleted again.
- The BLAKE3 of the image bytes comes from Rust (a small `#[frb(sync)]`
  function, or returned by the write call – builder's call); no Dart blake3
  package.
- The playing song is reloaded as today (`reloadIfCurrent`); mini player,
  Now Playing and the lock screen show the new cover (they follow the row –
  verify, including the `audio_service` artwork).

**Rust:** `write_tags` today knows `cover: None` = untouched and `Some` =
replace all pictures with one front cover. It gains a remove case
(e.g. an enum keep / set / remove, or a `remove_cover` flag – builder's
call) for MP3, M4A (incl. DASH-fragmented), FLAC and WAV. Rust tests: remove
on each format keeps audio and other tags; set-then-remove leaves no picture.

**Album/artist pages** show the new cover right away (they derive from the
tracks). Grouping by album is unaffected (covers are not part of the album
key – verify).

### 3 · Multi-select in Songs

Spec: `docs/mockups/roadmap-v1/04-songs-select.html`.

- **Entry:** "Select" (checkmark-circle icon) in the "…" menu, shown only on
  Library → Songs with at least one song, like the sort section.
- **State:** a provider (e.g. `songSelectionProvider`: off, or a set of track
  ids), because the title row, the bottom of the shell and the Songs list all
  react to it. Ids of songs that disappear (deleted, also by a running
  import's rollback) drop out of the set.
- **Title row while selecting:** the title reads "<n> Selected" ("Select
  Songs" at 0 – my call); the "…", "+" and downloads buttons are replaced by
  a "Done" pill (accent text). The Songs | Albums | Artists tabs stay
  visible; switching to another sub-tab or main tab ends selection mode.
- **Rows:** a round check circle left of the artwork (filled accent with a
  checkmark when selected). Tap toggles; long-press menu, playback on tap and
  the currently-playing highlight action are off while selecting. The meta
  line reads "<count> songs · tap to select". Search filter, sort and the A–Z
  index keep working; the selection survives filtering (hidden songs stay
  selected and are included in actions – my call, matches iOS Photos).
- **Selection bar** at the bottom, replacing the mini player and the tab bar
  while selecting: "Edit Info" (pencil), "Add to Playlist" (disabled until
  M4), "Delete" (red, trash). Edit Info and Delete are disabled at 0.
- **Edit Info** opens `openEditInfo` with the selected tracks (1 selected =
  the single-song editor with Title and Track). After a Save, selection mode
  ends; after Cancel it stays.
- **Delete** asks first: "Delete <n> songs?" / "This removes them from your
  library and deletes the files." with Cancel / Delete (red). Deletes one by
  one via `TrackRepository.delete`; failures are collected and shown in one
  dialog with selectable text (like Edit Info's save failures). Selection
  mode ends afterwards. Songs in the queue leave it as today.
- Back gesture / Android back while selecting ends selection mode instead of
  leaving the screen.

### 4 · Deferred v0.6.0 fixes

- Retry of a failed/cancelled download skips the "already in library"
  (duplicate `sourceKey`) guard – it must check again.
- The downloads button in the title row (`downloads_button.dart`) shows its
  success checkmark for 3 s whenever the queue goes idle without a failure,
  so cancelling the last job shows "done". After a cancel (no job finished
  since the queue became active) it must not show the checkmark (my call on
  what the deferred finding meant).
- Stale comments in `lib/import/import_controller.dart` and
  `lib/app/providers.dart`.
- `TrackRepository.hasSourceKey` is unused – remove it and its test (unless
  the retry fix uses it).
- Download rows rebuild on every progress tick – limit rebuilds to the row
  whose job changed.
- Double "Couldn't" prefix in a download error message (e.g. "Couldn't
  download: Couldn't write the tags: …") – one prefix only.
- CLAUDE.md: the downloader paragraph says AVPlayer handles the DASH M4A –
  reword to what was actually verified on the iPhone (it plays).

## Testing

- Unit: crop rectangle math (start scale/offset, clamping, pixel rect),
  cover making (crop, max 1000 px, no upscale, EXIF orientation, JPEG out),
  `TagEdit` with cover changes, `TagSaver` cover rules (skip, set, remove,
  partial failure keeps rows and cleans up the new cover file), selection
  provider (toggle, drop deleted ids).
- Widget: text tabs (switching, hidden when empty), cover block states
  (own, none, common, Mixed, pending), cover menu rows, crop page buttons,
  selection mode (enter, title count, Done, toggle, bar actions, delete
  confirm, leaves on tab switch).
- Rust: remove cover on all four formats; set then remove.
- Integration (`integration_test/`, real Rust + DB): set a cover on two real
  files, re-read their tags; remove it again.
- iPhone check before tagging (besides the early HEIC check): Photos picker, crop
  gestures, cover in mini player / Now Playing / lock screen, selection bar
  above the home indicator.
