# v0.8.0 SoundCloud Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A SoundCloud tab in Search Online. It searches tracks and downloads free ones as M4A (AAC HLS joined into one fragmented MP4, with the duration patched in), through the existing queue, Download sheet and Importer. Retry continues a stopped download, for YouTube as well.

**Architecture:** `OnlineSource` gets a third implementation, `SoundcloudSource`, built on a small `SoundcloudClient` (it scrapes and caches `client_id`) and pure parsers. `ResolvedStream` becomes sealed: `RangedStream` (YouTube, as today) or `SegmentedStream` (HLS init + media segments). `downloadStream` downloads both kinds and keeps a checkpoint next to the part file. `DownloadController` keeps a failed or cancelled job's folder, so Retry resumes. The UI adds the tab, the row variant and the sheet's source line.

**Tech Stack:** Flutter 3.50 / Dart 3.14, flutter_riverpod 3, `dart:io` HttpClient behind `HttpTransport`, Rust `write_tags` / Importer unchanged. Tests: flutter_test, the `integration_test` package with the real Rust core, and ffmpeg for fixtures.

**Spec:** `docs/superpowers/specs/2026-11-25-v0.8.0-soundcloud-design.md`. It is the authority. Read it first, including "Recon", "Calls made" and "Left to the builder". Mockup: `docs/mockups/roadmap-v1/08-online-results-soundcloud.html`. It shows two tabs, but the spec's three tabs win.

## Global Constraints

- Imports: `package:material_ui/material_ui.dart` and `package:cupertino_ui/cupertino_ui.dart`. Everything is in English.
- `flutter analyze` must report "No issues found!", `dart format` must leave no changes, and `flutter test` must be green.
- **No new packages.**
- Every SoundCloud host, path, query parameter, regex and size suffix lives in `lib/data/sources/soundcloud/soundcloud_api.dart`.
- Nothing secret or signed is committed. Fixtures are scrubbed of `client_id`, `track_authorization` and signed query strings. The `client_id` is only ever scraped at runtime.
- Exact strings:
  - Tab: "SoundCloud". Field: "Search SoundCloud".
  - Notes: "Protected", "Preview only", "Not available".
  - Source line: "From SoundCloud · M4A, 160 kbps" or "From SoundCloud · M4A, 96 kbps".
  - Subtitle: "{username} · {count} plays".
  - Errors: "SoundCloud didn't answer: HTTP {code}", "SoundCloud changed something; owntune needs an update", "No connection".
  - Resolving a non-downloadable track: "Protected: this track can't be downloaded", "Preview only: this track can't be downloaded", "Not available: this track can't be downloaded".
- `sourceKey` = `soundcloud:<track id>`. The settings value is `soundcloud` (the enum name), and the cached id lives under the settings key `soundcloud_client_id`.
- Transcoding choice: unencrypted `format.protocol == 'hls'`, `mime_type` starting with `audio/mp4`, preset `aac_160k` before `aac_96k`, `snipped == false`. Policies `SNIP` and `BLOCK` are never downloadable.
- Artwork: replace `-large` with `-t300x300` (row) or `-t500x500` (file cover). Use `artwork_url` if set, else `user.avatar_url`.
- Duration patch: write the sum of the playlist's `#EXTINF` values into `mvhd` (movie timescale), every `tkhd` (movie timescale) and every `mdhd` (that box's timescale), for both version 0 (32-bit) and version 1 (64-bit) boxes.
- Job folders: kept when a job ends as failed or cancelled; deleted when it ends as done or duplicate, when `clearFinished` drops it, and at startup (unchanged).

## Review Focus

1. **The signed segment URLs expire after ~2.5 h** (`expires=` in the query). A very slow 3 h mix can hit HTTP 403 partway. It must fail with "Download failed: HTTP 403 after X of Y MB", and Retry must re-resolve and continue from the checkpoint. Test in Task 3 and Task 4.
2. **A playlist that is encrypted, a master playlist, or one without `#EXT-X-ENDLIST`**, even though the API said `hls`. It must fail with a readable error before anything is written, never produce a file of encrypted bytes. Test in Task 2.
3. **`client_id` goes stale while the app runs.** The API answers 401 or 403. The client must scrape a new id once, repeat the request once, and fail normally if the second try also fails. Two searches running at once must cause one scrape, not two. Test in Task 5.
4. **Cancel while 4 segment requests are in flight.** The job must stop at once. Nothing written after the cancel may land in the file, and the checkpoint must match the bytes on disk. Test in Task 3.
5. **A track title with only an uploader and an emoji or non-Latin title** (e.g. "NHẠC NGHE ĐI TẮM 🎧"). The tags, the file name and the subtitle must keep the text, and the file name rules of `downloadFileName` must still apply. Test in Task 5 (tags) and Task 4 (existing file-name tests stay green).

### Task 3: Segmented download and resume

**Files:**

- Produces:
  - `Future<void> downloadStream(HttpTransport http, ResolvedStream stream, File target, {required void Function(int received, int total) onProgress, required CancelToken cancel, int chunkBytes = 10 << 20, int parallel = 4})`.
  - The checkpoint file is `File('${target.path}.progress')`. Its JSON is `{"shape": String, "bytes": int, "done": int}` and is written after every completed chunk or segment.
    - Ranged: `shape` is `ranged:<contentLength>` and `done` equals `bytes`.
    - Segmented: `shape` is `segmented:<segment count>:<patched init length>` and `done` is the number of segments written.
  - Test helper `serveSegments(Map<String, List<int>> byPath, {int Function(String path)? status})`. It returns an `onGet` handler that answers by `url.path`, with 404 for unknown paths.

- [ ] **Step 1:** Add tests. The segmented ones use a real init built with the Task 2 test helper, or a recorded tiny init, and 5 segments of 1,000 bytes.
  - `a segmented stream writes the patched init and then every segment in order`: file = patched init + seg0..seg4.
  - `fetches at most 4 segments at once and still writes in order`: the fake delays seg0 longest and counts concurrent requests; max ≤ 4, and the order is correct.
  - `progress is segment-based`: the last call is `(n, n)`. After k of 5 segments, `received/total` equals `k/5` within 1e-9.
  - `an HTTP 403 on segment 3 fails with "Download failed: HTTP 403 after …" and leaves a checkpoint with done=3`.
  - `resume continues after the checkpoint and fetches only the missing segments`: second run, same shape; `gets` holds the init and seg3, seg4, but not seg0–seg2.
  - `a partly written segment is cut off before continuing`: append 100 junk bytes after the checkpoint's `bytes`; the result is still exact.
  - `a different shape starts over`: 6 segments on the second run means all are fetched and the file is exact.
  - `cancel with requests in flight stops at once and the checkpoint matches the file length`.
  - `a ranged stream resumes from the checkpoint with the next range`: the range starts at the checkpoint's bytes.
  - `a ranged stream with another content length starts over`.
- [ ] **Step 2:** Run `flutter test test/download/stream_download_test.dart`. Expected: the new tests FAIL and the old ones PASS.
- [ ] **Step 3:** Implement.
  - Resume: if the checkpoint and the target both exist and the shape matches, truncate the target to `bytes` and continue from `done`. Otherwise delete both and start fresh.
  - Segmented: always fetch the init first, because the shape needs its patched length. On a fresh start, write it.
  - Segments are fetched into memory in a sliding window of `parallel` requests and written strictly in index order. After each write, `flush` the sink and then write the checkpoint.
  - Progress: when `done == 0` report `(received, stream.estimatedBytes)`; otherwise report `(received, received * count ~/ done)`. When finished, report `(received, received)`.
  - Error messages reuse today's wording, with MB as today: "Download failed: HTTP {code} after {x} of {y} MB" and "Download stopped at {x} of {y} MB (connection lost)". A signed URL never appears in a message.
