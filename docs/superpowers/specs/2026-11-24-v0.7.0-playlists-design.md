# v0.7.0 — Playlists (first half of M4)

## Intent

owntune has had a Playlists tab since v0.3.1, but it is an empty placeholder, and "New Playlist" (in the "+" menu) and "Add to Playlist" (in the multi-select bar) are disabled. v0.7.0 makes playlists real: create, fill, play, reorder, rename, give a cover, delete. It follows the approved roadmap mockups `docs/mockups/roadmap-v1/11–15`. Interactions follow Spotify where the mockups leave things open (see the memory note on Spotify as the player UI reference).

v0.7.0 also adds a **"…" button on the right of every song row** (Library and playlists), like Spotify, which opens the same song menu that long-press opens today. Long-press keeps working.

Home (the second half of M4) is a separate release after this one. Custom albums are dropped from M4 (the Edit Info album tag covers them); CLAUDE.md's milestone line is updated accordingly.

## Goals

- Playlists stored in the database: name, optional custom cover, ordered entries. A song can be in a playlist more than once.
- Playlists tab (mockup 11): a list of playlists with a search field and a "New Playlist" row; each row shows the cover (custom or mosaic), name and "N songs · duration".
- New Playlist (mockup 15): a sheet with Cancel / New Playlist / Create, an "Add Cover" tile and a name field. Hint text: "Without a cover, the playlist shows its first four albums." Opened from the "+" menu, from the Playlists tab, and from the top of the Add to Playlist sheet.
- Playlist detail (mockup 12): big cover, name, "N songs · duration", Play and Shuffle, the songs in playlist order. Tapping a song plays the playlist from that song (the playlist becomes the queue, source label = playlist name), the same as albums.
- Edit Playlist (mockup 13): Cancel / Edit Playlist / Done; Edit Cover (same cover menu as Edit Info: Choose from Photos, Choose File, Remove Cover; same crop page), rename, drag to reorder, remove songs (a remove control per row). Changes apply only on Done; Cancel discards them.
- Delete Playlist: from the "…" menu on the playlist detail page, with a confirm dialog. Only the playlist goes; the songs stay in the library.
- Add to Playlist (mockup 14): a sheet titled "Add to Playlist" with the song's title (or "N songs"), "New Playlist…" on top, then all playlists. Picking one appends the songs at the end. If any of the songs is already in that playlist, ask Spotify-style: "Already added" — "Add anyway" / "Don't add" (for several songs: add all, or add only the new ones). Reachable from:
  - the song menu ("Add to Playlist…"), everywhere the song menu exists (Songs, Search, album/artist pages, playlist detail, Now Playing),
  - the multi-select bar in Songs (the button that is disabled today),
  - the "…" menu on album and artist pages (adds all their songs in page order).
- Playlist song menu: on the playlist detail page the song menu also has "Remove from Playlist" (removes that one entry, not other copies of the same song).
- "…" button on song rows: `SongRow` (Songs, Search, artist page, playlist detail) and the album page's track rows get a trailing "…" (`CupertinoIcons.ellipsis`, muted colour, at least 44 pt tap target) that opens the song menu anchored at the button. Hidden in selection mode (the check circle takes over). Now Playing / Up Next are unchanged.
- Deleting a song from the library removes its playlist entries. Playlists that become empty stay.
- Covers: a custom cover is stored like song covers (`covers/<hash>.jpg`, ≤1000 px JPEG through the existing `uprightCover` / `cropCover`). Without one, the playlist shows a 2×2 mosaic of the covers of the first four distinct albums (by playlist order) that have a cover; with fewer than four, the first one fills the tile; with none, the default placeholder artwork.
- The Linux/test-friendly patterns stay: logic testable without Rust, dependencies via providers, errors shown in dialogs.

## Non-goals

- Home tab (next release).
- "Save to Playlist…" in the download sheet (later).
- Smart/automatic playlists, folders, M3U import/export, sharing.
- Writing playlist info into audio files (playlists live only in the database).
- Sorting the Playlists tab (fixed order, see below).
- Reorder/remove directly on the detail page outside Edit Playlist.

## Anti-goals

- Losing a song's playlist membership when its tags are edited (entries point at track ids, not tags).
- Deleting a cover file that a playlist still uses (or vice versa) — see Constraints.
- An edit that half-applies: Done writes name, cover, order and removals in one transaction.

## Constraints

- Covers are shared between tracks and playlists in `covers/`. **Every "is this cover still referenced" check must also look at `playlists.cover_file`:** `TrackRepository.isCoverReferenced` (used by delete and by `TagSaver`), and `cleanupOrphans` at startup (keep set = track covers ∪ playlist covers). Replacing or removing a playlist cover deletes the old file only if nothing references it any more.
- The database stores file names only, never paths.
- drift schema goes from 2 to 3; migration creates the two tables. `database.g.dart` is regenerated and committed (CI checks).
- Foreign keys: SQLite enforces `ON DELETE CASCADE` only with `PRAGMA foreign_keys = ON`, which is off today. Don't rely on it; delete entries explicitly in `TrackRepository.delete` and when a playlist is deleted (or turn the pragma on in `beforeOpen` — builder's choice, but test it).
- UI strings in English; imports via `material_ui` / `cupertino_ui`.
- iOS-specific parts (photo picker for the cover) are already proven in v0.6.1; no new platform code.

## Approaches

1. **Two drift tables `playlists` + `playlist_entries` (picked).** Fits the existing source of truth (drift), allows duplicates and order through an entry id + position, reactive through drift streams like `tracksProvider`.
2. JSON list in `settings_entries`: no new tables, but no streams per playlist, no referential cleanup, and covers/ordering become string juggling. Rejected.
3. M3U files in the library folder: portable, but the DB would no longer be the source of truth and file names would need syncing. Rejected.

The user approved approach 1 and the design summary on 2026-11-24.

## Data model (decided)

```
playlists
  id          int, autoincrement
  name        text
  cover_file  text, nullable   -- covers/<name>
  created_at  datetime

playlist_entries
  id           int, autoincrement   -- an entry's own key (duplicates allowed)
  playlist_id  int  -> playlists.id
  track_id     int  -> tracks.id
  position     int                  -- 0..n-1, dense, rewritten on reorder/remove
```

Index on `playlist_entries (playlist_id, position)`.

## Behaviour details (decided)

- Playlists tab order: most recently created first (`created_at` desc), the mockup shows no sort control.
- Names: trimmed, must not be empty (Create/Done disabled otherwise); duplicate names are allowed.
- "N songs · duration": "1 song", durations like the album page ("1 h 7 min", "44 min").
- Search field on the Playlists tab filters by name, same style as the Library sub-tab searches.
- Shuffle/Play on the detail page behave like on album pages (Play turns shuffle off, Shuffle turns it on).
- The queue holds track ids, as today; editing the playlist while it plays doesn't change the running queue.
- Back label of screens opened from a playlist: the playlist name (or "Playlists" for the detail page itself).
- After "New Playlist…" from Add to Playlist, the new playlist is created and the songs are added to it straight away.
- A brief confirmation after adding is the builder's call (e.g. a short toast/snackbar "Added to <name>"); errors go into a dialog.
- *(Orchestrator's calls after the builder check:)*
  - The playlist detail page gets a "…" button in its title row (like album/artist pages) with **Edit Playlist** and **Delete Playlist**.
  - "Remove from Playlist" in the song menu is intended; the non-goal only excludes inline drag handles/remove controls on the detail page.
  - Tapping a song plays from that entry's position (matters with duplicates), not from the first entry with the same track id.
  - A cover picked in Edit Playlist is stored in `covers/` only on Done; Cancel leaves no file behind.
  - Entries whose track is deleted while Edit Playlist is open are dropped on Done.
  - Multi-select ends after Add to Playlist (like after Delete).
  - Duplicate prompt with several songs: songs already in the playlist count as duplicates; repeats inside the selection itself are added as selected (no prompt for them).
