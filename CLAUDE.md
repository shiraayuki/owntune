## Project

owntune is a mobile music player for **local files** (iOS & Android): import, play, and manage metadata/covers/albums/playlists. No streaming, no account; playback is fully offline (the network is only used to search and download songs, since v0.6.0).

## Constraints that shape every decision

- Development happens on **Linux, without a Mac**. Daily loop: Flutter as a **Linux desktop app** (`flutter run -d linux`) or in the **Android emulator**, with hot reload.
- **iOS is never built locally.** The `.ipa` is produced only by GitHub Actions (`.github/workflows/ios.yml`) and sideloaded with SideStore (free Apple ID; the app expires after 7 days). The Android `.apk` for releases is also built in Actions (`.github/workflows/android.yml`), signed with the owntune release key.
- The iOS workflow runs **only on version tags `v*` (called by the Release workflow) or manually** (`gh workflow run iOS`), not on every push — macOS runners often have long queues. Default runner is the Intel `macos-15-intel`, because arm64 runners (`macos-latest`) at times were not assigned at all; switchable via a dispatch input.
- iOS-specific behavior (background playback, lock screen, Files app) is **only testable on the real iPhone**. Keep platform code small and behind interfaces; logic must stay testable on Linux. For iOS-sensitive work, trigger an iOS build manually in between.
- Without a Mac there are no logs on the iPhone. Startup failures must therefore be **visible in the UI** instead of crashing the app (pattern: `startUp()` never throws and returns `StartupFailed`, which `StartupErrorApp` shows as selectable text inside a scroll view; later errors such as a failed import or delete are shown in sheets or dialogs; the import sheets sit above the navigator via `MaterialApp.builder`, so they also show over pushed screens).
- The Linux target is a development aid only, not a product.

## Tech stack and pinned versions

Flutter **3.50.0** (pinned in both workflows via `FLUTTER_VERSION`) · Dart 3.14 · Rust stable · flutter_rust_bridge **2.13.0** · lofty **0.25.5**.

- flutter_rust_bridge must be **exactly equal in three places**: `pubspec.yaml`, `rust/Cargo.toml` (`=2.13.0`), and the installed `flutter_rust_bridge_codegen` (`FRB_VERSION` in `ci.yml`). Otherwise `RustLib.init()` fails at runtime.
- Since Flutter 3.47, `package:flutter/material.dart` is deprecated → import **`package:material_ui/material_ui.dart`** (otherwise `flutter analyze` reports infos and CI fails).
- Since 3.50, `package:flutter/cupertino.dart` is deprecated too → import **`package:cupertino_ui/cupertino_ui.dart`** (icons: `CupertinoIcons`).
- In use since v0.2.0: flutter_riverpod 3 (no codegen), drift + drift_flutter (+ drift_dev/build_runner), file_picker, path_provider, package_info_plus; Rust side: blake3.
- In use since v0.4.0: just_audio (iOS/Android), just_audio_media_kit + media_kit_libs_linux (Linux, needs system libmpv; CI installs `libmpv-dev`), audio_session (iOS/Android: music category, so the silent switch does not mute).
- In use since v0.6.0: image (cover crop/re-encode for downloads).
- In use since v0.4.1: audio_service (iOS/Android; `MainActivity` extends `AudioServiceActivity`, the manifest declares its service and media button receiver, `Info.plist` has `UIBackgroundModes: audio`). Add packages only with the milestone that needs them.
- **Linux runner links `libgcc_s` first** (`linux/runner/CMakeLists.txt`): `libflutter_linux_gtk.so` exports its own `_Unwind_*`, and LuaJIT inside libmpv segfaulted when it unwound through them. Keep that line when regenerating the Linux runner.
- **media_kit reports an unreadable file only as an event with an error code** and never completes the load; `JustAudioEngine.load` therefore also ends on that event.

**Release:** `git tag vX.Y.Z && git push --tags` → `release.yml` ("Release") calls `ios.yml` and `android.yml` in parallel and, only when both succeed, creates ONE GitHub release with `owntune.ipa`, `owntune.apk` and `source.json` (a re-run of its publish job replaces the files), so `releases/latest/download/*` never points into a half-filled release. Version and build number come from the tag via `tool/release_version.sh` (build number = major·10000 + minor·100 + patch, e.g. 0.8.2 → 802; the same for both platforms and SideStore's `buildVersion`; minor and patch stay below 100). SideStore source (add once in SideStore): `https://github.com/shiraayuki/owntune/releases/latest/download/source.json`; generated by `tool/sidestore_source.dart` (tests in `test/tool/`). `gh workflow run iOS` / `gh workflow run Android` build an artifact only, no release.

**Android signing:** `android/app/build.gradle.kts` signs release builds with the owntune key from the env vars `OWNTUNE_KEYSTORE` (path), `OWNTUNE_KEYSTORE_PASSWORD`, `OWNTUNE_KEY_ALIAS`, `OWNTUNE_KEY_PASSWORD`, or from a git-ignored `android/key.properties` (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`); without either it falls back to the debug key (CI's test APK, `flutter run --release`). The Android workflow takes the key from the secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, fails when one is missing and checks the APK's certificate against the keystore. The keystore (PKCS12, alias `owntune`) and its password live outside the repo in `~/.local/share/owntune-signing/` and must be backed up: **without that exact key an update cannot be installed over the old app**. The APK is universal (arm, arm64, x86_64); do not restrict `--target-platform`, some packages (jni, the Rust crate) then still ship x86_64 libraries without `libflutter.so`.

**Download page** (`site/`): when the UI of a shown screen changes (Home, Library, Now Playing, playlist page, Search Online, Edit Info, Stats, or the mini player on them), update `site/screens/*.html` (corrections live in `fixes.css`) and run `tool/make_screenshots.sh` so the README images follow. The page reads the latest release's version and date from the GitHub API at runtime; its copy must not promise what the app does not do.

**Downloader** (`lib/data/sources/`, `lib/download/`): an own small innertube client, no package. Search: YouTube Music (`WEB_REMIX`, songs filter) and YouTube (`WEB`, videos filter); download: the player call as the **visionOS** client (`VISIONOS`), which gets direct audio URLs without PO token or JavaScript (yt-dlp's `_DEFAULT_JSLESS_CLIENTS`) but needs a `visitorData` from a search response (else "Sign in to confirm you're not a bot"). **Every client value lives in `lib/data/sources/youtube/innertube_clients.dart`**; when YouTube breaks it, compare with yt-dlp's current `INNERTUBE_CLIENTS`/`_DEFAULT_CLIENTS` and release. The file is fetched with `&range=` chunks of 10 MB (a plain GET is refused), is a DASH-fragmented MP4 (brand `dash`) that lofty and libmpv read and that plays on the iPhone (checked in v0.6.0). `DownloadController` runs one job at a time: resolve → `<temp>/owntune-download/<job>/audio.part.m4a` → cover (`prepareCover`, 16:9 thumbnails cropped square, in an isolate) → Rust `write_tags` with `cover` → rename to "Artist - Title.m4a" → `Importer.importFiles(sourceKeys:)` (the Importer queues calls, so a download waits for a running Import Music) → the job folder is deleted in every outcome; startup empties `<temp>/owntune-download`. Parser tests run against `test/fixtures/online/*.json` (recorded and scrubbed of IPs/visitorData by `tool/record_online_fixtures.sh`); the live test is opt-in.

**Link lookup** (v0.8.1; `lib/data/sources/online_link.dart`): the pure `parseOnlineLink(text)` returns `YoutubeLink(videoId)`, `SoundcloudLink(url)`, `UnsupportedLink(message)` or null (search as text); `OnlineSource.lookup(link)` builds one `OnlineResult` (YouTube: the player call's `videoDetails` like a video result; SoundCloud: `resolve?url=` parsed by `parseSoundcloudTrack`); `SearchOnlineScreen` picks `sources[youtube]` or `sources[soundcloud]` by link type on submit or when the text grows by more than one character at once (a paste), and a newer action or an edit of the field drops a late answer.

**SoundCloud** (v0.8.0; `lib/data/sources/soundcloud/`, `lib/data/sources/hls.dart`, `lib/download/mp4_duration.dart`): an own client against SoundCloud's web API (`api-v2.soundcloud.com`), no package. **Every host, path, query parameter, regex, preset and artwork size lives in `soundcloud_api.dart`**; when SoundCloud breaks it, fix that file (and `tool/record_online_fixtures.sh`, which uses the same values) and release. SoundCloud no longer serves progressive MP3, only HLS: a track is downloadable when it has an unencrypted `hls` transcoding with `audio/mp4` and preset `aac_160k` (else `aac_96k`) that is not `snipped`, and its policy is not `SNIP` or `BLOCK`; label tracks offer only encrypted HLS ("Protected", never downloaded, no DRM workarounds). The API wants a `client_id` that the app scrapes at runtime from the scripts of soundcloud.com (scripts from the last to the first until one matches) and caches in `settings_entries` (`soundcloud_client_id`; `SoundcloudClientIdStore`); on a 401 or 403 the client scrapes a new one once and repeats the request once, and concurrent calls share one scrape. The `client_id` and signed URLs are never committed: fixtures are scrubbed. `resolve` fetches the track again (fresh transcodings and `track_authorization`), asks the transcoding URL for the media playlist URL and parses the playlist with `parseMediaPlaylist` (`hls.dart`): it must be an unencrypted fMP4 media playlist with `#EXT-X-MAP` and `#EXT-X-ENDLIST`, else it fails as protected or changed before anything is written. `ResolvedStream` is now sealed: `RangedStream` (YouTube) or `SegmentedStream` (init URL, segments with their `#EXTINF` durations, bitrate). `downloadStream` (`stream_download.dart`) fetches segments four at a time in a sliding window and writes them strictly in order after the init segment, in which `patchMp4Duration` has written the sum of the `#EXTINF` values into `mvhd`, every `tkhd` (movie timescale) and every `mdhd` (that box's timescale), versions 0 and 1: a fragmented MP4 keeps its durations in the fragments, so lofty would read 0 and the Importer would store an empty song (an integration test with a real ffmpeg HLS fixture proves it). After each completed chunk or segment a checkpoint `<target>.progress` (shape, bytes, done) is written; Retry resolves again (signed URLs expire after about 2.5 h) and continues from it when the shape matches (same segment count and init size, or same content length), cutting a half-written tail off, else starts over. For that, the job folder in `<temp>/owntune-download/` is **kept when a job fails or is cancelled**; it is deleted when the job is done or a duplicate, when `clearFinished` drops it, and at startup. A cancel stops all in-flight requests at once and nothing written after it lands in the file. Errors name the service ("SoundCloud didn't answer: HTTP 429", "SoundCloud changed something; owntune needs an update", "No connection"; `HttpTransport` takes the service name). Tags: `soundcloudTags` splits "Artist - Title" like `guessTags` (drops "(FREE DL)"-style noise), else title = track title, artist = `publisher_metadata.artist` or the uploader; album from `publisher_metadata`, genre and year from the track go into the file without showing in the sheet; artwork is `artwork_url` (else the avatar) with `-large` replaced by `-t300x300` (row) or `-t500x500` (cover, square, no crop). `sourceKey` is `soundcloud:<track id>`. Tests: parsers and playlist against `test/fixtures/online/soundcloud_*`, the real-core pipeline in `integration_test/download_test.dart` against the ffmpeg fixture `hls.m3u8` + `hls_init.mp4` + `hls_seg*.m4s` in `test/fixtures/audio` (init with `mvhd` duration 0, made by `tool/make_fixtures.sh`), and the opt-in live test (search, resolve, init and first segment).

**Player** (`lib/player/`): **On completion the controller pauses the engine before loading the next entry** (just_audio keeps `playing` true after the end, so a `play()` alone would be a no-op; on iOS the next song stayed silent). `PlayerController` (Riverpod notifier) owns a pure `PlayQueue` (entries with their own keys, current index, `QueueSource`, repeat) and drives an `AudioEngine` that plays one file at a time; tests use `FakeAudioEngine` (`pumpApp` overrides `audioEngineProvider`). The controller stores track ids and follows `tracksProvider`, so deleted songs leave the queue. The system controls sit behind the `SystemControls` interface (`lib/player/system_controls.dart`): `AudioServiceControls` on phones, `NoSystemControls` on Linux and in tests; `systemControlsSyncProvider` publishes the current song to them and sends their commands (play, pause, next, previous, seek) to the controller. Shuffle: while shuffled, the queue's `entries` are the play order and `original` keeps the unshuffled order (`shuffleOn`/`shuffleOff`/`following` in `play_queue.dart`); the order comes from `spread()` (`shuffle.dart`) with `randomProvider`. The controller saves a `PlayerSnapshot` (track ids, index, source, repeat, position, `shuffleOrder` = positions of the unshuffled order) as JSON in `settings_entries` after queue changes, on pause and every five seconds of playback, and restores it paused, without songs deleted since. The mini player lives in each Scaffold's bottom bar (shell and detail screens), so menus dim it. **Queue source and listen history (v0.7.1):** `QueueSource` (`queue_source.dart`: `QueueSourceKind` songs/album/artist/playlist/liked/search/queued/other, optional key, label) replaces the old label string; the snapshot saves `sourceKind`/`sourceKey` (an old label-only snapshot restores as `other`) and the positions of entries added with Play Next / Later, which carry a `queued` flag and are recorded as kind `queued`. A pure `ListenSession` (`listen_session.dart`) adds up the forward steps of the engine position while playing: a seek or a step larger than 3 s adds nothing, and the baseline resets on load and on every `seek`. **A play counts at 30 s heard**, or when the song plays to its end with at least 1 s heard and either is shorter than 30 s or was heard all but the last 3 s (once per session; a seek to the end counts nothing): then `play_count` + 1 and `last_played_at` are written; skipping at 10 s counts nothing. Each queue entry (and each round of repeat one) is its own session; a pause of 30 min or more ends the session on resume (the new one starts from zero), while `reloadIfCurrent` keeps it. A session writes one `plays` row through `PlayRepository` once it has 1 s heard, and updates it at the save points (every five seconds, on pause, on queue changes) and when it ends. These writes go through one sequential chain, are never awaited by playback and swallow their errors, so history can never stop a song. `clockProvider` supplies the wall clock (injected in tests).

**Playlists** (`lib/playlists/`, `lib/data/playlist_repository.dart`): drift schema v3 adds `playlists` (id, name, cover_file, created_at) and `playlist_entries` (id, playlist_id, track_id, position; the same song may appear several times) with the index `playlist_entries_order`. The foreign-key pragma stays off, so entries are deleted explicitly: `TrackRepository.delete` removes a track's entries and renumbers, `PlaylistRepository.delete` removes the playlist's. `PlaylistRepository` offers create, addTracks, removeEntry, saveEdit (name, entry order/removals and `PlaylistCoverChange` Keep/Set/Remove in one transaction) and delete. `playlistsProvider` resolves the rows against `tracksProvider` into `PlaylistView`s (entries of deleted songs are left out; the mosaic shows the covers of the first four distinct albums; `formatTotalDuration`). **Shared covers rule:** a cover file may be used by tracks and playlists at once (same hash, same file), so every check whether a cover can be deleted goes through `isCoverInUse(db, name)` in `track_repository.dart`, which looks at both, and `cleanupOrphans` keeps both. `pickAndCropCover` (`lib/edit/cover_flow.dart`) is the pick + crop flow shared by Edit Info and the playlist screens. Edit Playlist applies everything on Done only; Add to Playlist asks "Already added" before adding songs a playlist already has. Song rows (`SongRow`, `AlbumTrackRow`) have a trailing "…" button that opens the song menu (hidden in selection mode). **Schema v4 (v0.7.1)** adds `tracks.liked_at` (nullable; null = not liked; `TrackRepository.setLiked` keeps the date of an existing like, so a bulk add does not reorder) and the `plays` table (id, track_id, started_at, listened_ms, counted, source_kind, source_key; index `plays_started`). **Deleting a track keeps its `plays` rows** (the history is what was listened to; later Stats/For You skip rows whose track is gone), while `liked_at` goes with the row. Liked Songs is derived from `tracksProvider` (songs with `liked_at`, newest first), so the page follows a like or unlike from anywhere at once (`lib/playlists/liked_songs.dart`).

**Startup sequence** (`lib/app/startup.dart`): `RustLib.init()` → `initAudio()` (media_kit on Linux, audio session on phones) → system controls (`AudioService.init` on phones, none on Linux) → `LibraryStorage.open()` + `ensure()` (`<ApplicationSupport>/library/{audio,covers}`) → `AppDatabase.open()` (`<ApplicationSupport>/owntune.sqlite`) → `cleanupOrphans()` (best effort: leftover `.part` files and files without a row) → empty `<temp>/owntune-download` (best effort) → load settings → load the saved player state (a broken one is ignored). Any error → `StartupFailed`.

**Data rules:** The DB stores file names only (`<blake3>.<ext>`, covers `<blake3-of-image>.<ext>`), never absolute paths, because the iOS container path changes on app updates. Each file is copied to `audio/<random>.part.<ext>` (lofty picks the parser by extension), renamed to `<blake3>.<ext>`, and only then gets its row; covers are written via `covers/<random>.part`.

**Drift codegen:** `lib/data/db/database.g.dart` is committed; CI runs `build_runner` and fails if anything changes (same as for the FRB code).

**Rust bridge:** Functions in `rust/src/api/*.rs` are translated to `lib/src/rust/api/*.dart` by `flutter_rust_bridge_codegen generate` (e.g. `supported_formats()` → `supportedFormats()`; `#[frb(sync)]` = synchronous call). Generated code is committed; CI regenerates it and fails if anything changes. The codegen does not delete stale files — after removing a Rust module, delete the matching `.dart` file by hand.

**Testability:** Code that calls Rust takes the Rust functions as parameters (`startUp({initRust, openStorage, openDatabase})`, `Importer(read:, supportedExtensions:)`), and widgets get their dependencies via Riverpod providers that tests override (`pumpApp` in `test/support/fakes.dart`). So unit/widget tests run without the native library. Real Rust calls and the real database are tested in `integration_test/`.

## Principles for upcoming milestones

- **File storage:** Imported files are copied into the app-owned library folder `<ApplicationSupport>/library/`, because iOS does not allow persistent access to foreign folders. Duplicates are detected by BLAKE3 hash. In M1 the folder is deliberately **not** visible in the Files app: users could delete files behind the database's back. Revisit this together with "Open with …" in M5.
- **Metadata:** The database is the source of truth for display; changes are additionally written back into the file tags via `lofty` (ID3, Vorbis, MP4). Since v0.5.0: `write_tags` (Rust) writes the primary tag of a copy `<name>.part.<ext>` and renames it over the original; `TagSaver` writes each file first and updates only the rows whose file was written. `contentHash` and `fileName` keep their import values after an edit, so re-importing the original file is still a duplicate. Covers: v0.2.0 stores each distinct embedded image once under its hash and downscales in the UI (`cacheWidth`); real thumbnails may come later. Since v0.6.1 a cover change is part of `TagEdit` (`CoverKeep`/`CoverSet`/`CoverRemove`); `write_tags` replaces all pictures with the new front cover or, with `remove_cover`, removes them; `TagSaver` stores a new cover once as `covers/<hashBytes>.jpg` before writing, sets `coverFile` only on rows whose file was written, and deletes old cover files nothing references any more. Picked images go through `uprightCover` (EXIF orientation, ≤2000 px) and `cropCover` (≤1000 px JPEG) in isolates, called via top-level functions so the closures capture no widget state.
- **Downloads from YouTube are in scope since v0.6.0** (decided 2026-11-19: "the point of the app"; more maintenance accepted). SoundCloud followed in v0.8.0 as a second `OnlineSource`. Downloads are personal use in a sideloaded app that is not published in a store.

**Data model:** The `tracks` and `settings_entries` tables in `lib/data/db/database.dart` are the source of truth. Albums and artists are derived from track tags in Dart (`Library.from` in `lib/library/library.dart`, fed by `libraryProvider`); every view, the search and the song menu read that one snapshot. There is no album table (and none is planned: custom albums are covered by the Edit Info album tag). `playlists` and `playlist_entries` exist since v0.7.0 (see Playlists above) and, like everything else, store file names only, never paths. Since v0.7.1 (schema v4) a like is the nullable `tracks.liked_at` (there is no Liked Songs playlist row) and `plays` holds one row per listen; deleted tracks keep their plays.

## Milestones

- **M0 Skeleton** – ✅ done (release `v0.1.0`).
- **M1 Import & library** – MP3, M4A/AAC, FLAC, WAV (OGG later); multi-file import, copying, hash duplicates, read tags + cover; Songs/Albums/Artists views with search and sorting. *Done when:* 50 files imported and grouped correctly. Released in two parts: `v0.2.0` (import, database, Songs, delete, settings) and `v0.3.0` (Albums, Artists, details, search, sort); `v0.3.1` regroups them into four tabs with a Library tab.
- **M2 Player** – controls, queue, shuffle/repeat, mini and full-screen player, background + lock screen (`UIBackgroundModes: audio`), restore state after restart. *Done when:* plays on the iPhone with the screen locked and can be controlled. ✅ done. Released in three parts: `v0.4.0` (in-app playback, no shuffle), `v0.4.1` (background, lock screen, restore) and `v0.4.2` (shuffle).
- **M3 Metadata editor** – edit fields, pick/crop/remove covers, bulk editing, write back to tags. ✅ done: `v0.5.0` (Edit Info) and `v0.6.1` (covers, multi-select; released after the first Downloader part).
- **Downloader** – Search Online with download into the library. `v0.6.0` YouTube (songs and videos, single songs), `v0.8.0` SoundCloud (planned as v0.6.2); `v0.8.1` paste a YouTube or SoundCloud link; whole albums later.
- **M4 Playlists & Home** – playlists with drag & drop and custom cover (✅ `v0.7.0`), Liked Songs and the play history (✅ `v0.7.1`), then the Home tab: For You (✅ `v0.7.2`) and Stats (✅ `v0.7.3`). ✅ done: `v0.7.0` to `v0.7.3`.
- **M5 Polish** – share sheet / "Open with …", dynamic colors from the cover, further statistics (dark mode already ships in v0.2.0).

Out of scope: cloud sync, accounts, streaming, store publishing.
