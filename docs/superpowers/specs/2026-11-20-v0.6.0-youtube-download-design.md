# v0.6.0 – Download songs from YouTube (design)

Date: 2026-11-20 · Milestone: Downloader (new, between M3 and M4) · Release: v0.6.0 (YouTube), v0.6.1 (SoundCloud)

## Intent

owntune plays local files. What the user always missed in other players is getting a song into the library *from inside the app*: search, tap, done. v0.6.0 adds "Search Online": search YouTube Music (songs) or YouTube (videos), download the audio of a result, and it lands in the library with clean title, artist, album and a square cover, like any imported file. This reverses the old "download is out of scope" decision (CLAUDE.md is updated with this release).

Success: on the iPhone, searching "linkin park numb", tapping the first song and tapping Download puts "Numb · Linkin Park · Meteora" with its album cover into Library > Songs within seconds, and it plays, also with the screen locked.

## Goals

- "+" → **Search Online** (the disabled placeholder becomes active) opens a full-screen page.
- A segmented switch **Songs | Videos | SoundCloud** at the top. v0.6.0 implements Songs and Videos; the SoundCloud segment is **not shown** until v0.6.1 (the switch then has two segments in v0.6.0). The last used segment is remembered (settings).
- **Songs** = YouTube Music song search. Rows: square cover, title, artist, album, duration.
- **Videos** = YouTube video search. Rows: 16:9 thumbnail with duration, title, channel, views (mockup 07).
- **Recent searches** below the empty search field (last 10, newest first, per app not per source; tap = search again; mockup 06). A way to clear them: swipe a row to delete (builder may pick an equivalent).
- Each result row shows **"In Library"** when a track with that source id exists, and **"Downloading NN %"** / "Waiting" while a download for it is queued or running (mockup 07).
- Tapping a row opens the **Download sheet** (mockup 09) with Title, Artist, Album (editable text fields) prefilled, the cover, a source line ("From YouTube Music · M4A, 128 kbps" or "From YouTube · "<video title>" by <channel> · M4A, 128 kbps"), and **Download**. "Save to Playlist…" is **not** shown (comes with M4).
- A song that is already in the library (same source id) can still be opened in the sheet, but its button reads "In Library" and is disabled.
- **Downloads** run one at a time in a queue owned by the app (not the page): leaving Search Online does not stop them. A **Downloads sheet** (mockup 10) lists the queue: per song cover, title, status line ("Waiting", "1.2 of 3.0 MB", "Adding to library…", "Added to your library", "Couldn't download: <reason> · Retry"), a cancel button (X) while waiting/running, a check when done, a warning icon on failure; header "N of M done · keep owntune open until they finish"; a Done button that closes the sheet and clears finished/failed rows.
- The Downloads sheet opens from a **downloads button** in Search Online's top row, visible while the queue is non-empty (icon `CupertinoIcons.arrow_down_circle`, with the number of unfinished items as a small badge). It is also reachable after leaving Search Online: the same button appears in the app shell's title row while downloads are unfinished (my call: the "+" menu is the wrong place for status).
- A finished download goes through the normal **Importer**, so it appears in the library immediately (tracksProvider), with its cover.

## Non-goals (v0.6.0)

- SoundCloud (v0.6.1; the source abstraction is prepared now).
- Whole albums or playlists (a later release; YouTube Music album results are not shown in v0.6.0).
- Search result paging ("load more"): the first page (~20 results) only.
- Background downloads with the app suspended. iOS stops networking ~30 s after the app leaves the foreground; a download that fails that way shows its error and can be retried. No background URLSession.
- Format conversion. The file stays the AAC M4A that YouTube serves (itag 140). No Opus/WebM.
- Track number, disc number, year, genre from YouTube (not in the song search results; comes with album downloads).
- "Save to Playlist…" (M4).
- Logged-in YouTube, age-restricted or "made for kids" videos (the client used cannot fetch them; they fail with a readable reason).

## Anti-goals

- No server, no account, no API key, no yt-dlp binary, no JavaScript engine in v0.6.0.
- Never leave half files or rows behind: a cancelled, failed or interrupted download leaves nothing in `library/` and nothing in the DB.
- Never fail silently: every error reaches the UI with a reason that is readable on the iPhone (no logs there).
- Don't hammer YouTube: no requests on keystrokes (search runs on submit), no prefetching of streams, one download at a time.

## Constraints

- Development on Linux, iOS only via CI and sideloading (CLAUDE.md). The whole client must be testable on Linux; tests run offline against recorded JSON.
- **The YouTube approach is fragile by nature.** It relies on YouTube's private "innertube" API and on a client identity (visionOS) that YouTube currently serves without a PO token or JS challenges. yt-dlp has switched clients several times in 2026. Everything client-specific (client name, version, user agent, ids, search params) therefore lives in **one file** so a fix is a one-file change plus a release.
- Files are copied into `library/` and stored by name only (data rules in CLAUDE.md).
- Spike evidence (2026-11-20, branch `spike-youtube-ios`, throwaway): search (WEB_REMIX and WEB), player (VISIONOS) and range-chunked download of itag 140 work from a German residential IP for 6 videos; the downloaded file is a DASH-fragmented MP4 (major brand `dash`); lofty 0.25.5 reads and writes its tags; the real Importer imports it on Linux. **Checked on the iPhone (2026-11-20, spike build, CI run 44712542175):** search, VISIONOS player and download work over the phone's network, and the downloaded M4A imports and plays. So no remux is planned; the plan builds the pipeline as described below.

## Approaches considered

1. **Own small Dart client (picked).** `dart:io` HttpClient, three innertube calls (YouTube Music search, YouTube search, VISIONOS player) and a chunked downloader, ~300 lines, no new package for networking. Proven by the spike, testable with recorded JSON, every line under our control when YouTube changes something.
2. youtube_explode_dart: search for free, but its stream clients fail on the PO token (first spike: HTTP 403 after 1 MB); we would still write the player part ourselves and carry a large dependency.
3. In Rust (own HTTP or rustypipe): more iOS build work (TLS, cross-compiling), progress/cancel across the bridge, no gain. Rust becomes interesting only if a JS-challenge fallback (QuickJS) is ever needed; that would be added then, for that part only.

The user picked 1 (2026-11-20).

## Design

### Source abstraction (`lib/data/sources/`)

```
abstract interface class OnlineSource {
  String get id;                                   // 'ytmusic', 'youtube' (later 'soundcloud')
  Future<List<OnlineResult>> search(String query);
  Future<ResolvedStream> resolve(OnlineResult r); // direct audio URL, size, extension, bitrate
}
```

- `OnlineResult`: `sourceKey` (stable id, e.g. `youtube:5qZQEq_C3vc`; Songs and Videos share the `youtube:` prefix because they are the same video ids, so "In Library" works across both), display fields (title, subtitle parts, duration, views where present), thumbnail URL for the row, cover URL for the download (high resolution), and suggested tags (title, artist, album).
- `ResolvedStream`: `Uri url`, `int contentLength`, `String extension` (`m4a`), `int bitrate`, plus headers to send.
- Two implementations in v0.6.0, sharing one `InnertubeClient`:
  - `YoutubeMusicSource` (Songs): `POST https://music.youtube.com/youtubei/v1/search` with client `WEB_REMIX`, songs filter `params: EgWKAQIIAWoKEAoQAxAEEAkQBQ==`. Parse `musicResponsiveListItemRenderer`s: video id from `playlistItemData.videoId`; title = first flex column; artists = runs of the second column whose navigation endpoint is an artist page (joined with ", " if several; the literal separators " & ", ", " in the runs are kept as they appear), album = the run with an album browse endpoint, duration = the last `m:ss` run. Cover URL: the thumbnail URL with its `=w120-h120…` suffix replaced by `=w1200-h1200` (square album art).
  - `YoutubeSource` (Videos): `POST https://www.youtube.com/youtubei/v1/search` with client `WEB`, videos filter `params: EgIQAfABAQ==`. Parse `videoRenderer`s (id, title, owner, length, view count text). Row thumbnail and cover source: `https://i.ytimg.com/vi/<id>/hqdefault.jpg` for the row, `maxresdefault.jpg` (fallback `hqdefault.jpg` on 404) for the cover.
  - `resolve` (both): `POST https://www.youtube.com/youtubei/v1/player` as client `VISIONOS` (`clientVersion 1.02`, client id `101`, the Safari/macOS user agent, `deviceMake Apple`, `deviceModel RealityDevice17,1`, `osName visionOS`, `osVersion 26.5.23O471`), headers `X-YouTube-Client-Name`, `X-YouTube-Client-Version`, `Origin`, `X-Goog-Visitor-Id`, body with `videoId`, `contentCheckOk`, `racyCheckOk`. Requires `visitorData` in context and header: taken from the `responseContext.visitorData` of the last search response (any of the two), kept in memory; if none yet, one cheap YouTube Music search is made to obtain it. Pick `adaptiveFormats` itag 140; `playabilityStatus != OK` → error with YouTube's `reason`; no itag 140 → "No M4A audio for this video".
- All client constants (names, versions, user agents, ids, filter params, hosts) live in `lib/data/sources/youtube/innertube_clients.dart`.

### Title/artist guess for Videos (`guessTags`)

Pure function, unit-tested with a table of real titles:
1. Strip bracketed noise case-insensitively: `(Official Video)`, `(Official Music Video)`, `(Official Audio)`, `(Lyrics)`, `(Lyric Video)`, `(Visualizer)`, `[4K …]`, `(HD)`, `(HQ)`, `(Remastered …)` only when it contains "remaster" + a year or "4K", and similar; keep musically meaningful brackets (`(Live …)`, `(Acoustic)`, `(… Remix)`, `(feat. …)`).
2. Split on the first ` - `, ` – ` or ` — `: left = artist, right = title.
3. No separator: title = cleaned title, artist = channel name with ` - Topic`, `VEVO` suffix and `Official` removed.
4. Album: empty.

The guess only prefills the sheet; the user corrects it there.

### Download queue (`lib/download/`)

- `DownloadController` (Riverpod notifier, app-wide, like `ImportController`) owns a list of `DownloadJob`s: result, tags as confirmed in the sheet, status (`waiting`, `downloading(received, total)`, `importing`, `done`, `failed(reason)`, `cancelled`).
- One job runs at a time. Steps:
  1. `resolve` (fresh each attempt; stream URLs expire after hours).
  2. Download to `<temporary dir>/download/<random>.part.m4a` with `&range=start-end` chunks of 10 MB (plain GET without range is throttled/refused by YouTube); progress after every received block; cancel closes the connection and deletes the file.
  3. Download the cover (JPEG) to memory; for Videos center-crop the 16:9 thumbnail to a square (pure Dart, `image` package — new dependency, added with this milestone). A failed cover download does not fail the job (no cover then).
  4. Write tags and cover into the part file via Rust (see below).
  5. Rename to `<sanitized "Artist - Title">.m4a` in the same temp folder (that becomes the track's `originalName`), then import it with the Importer with the job's `sourceKey`. The Importer is shared with "Import Music" and allows one run at a time: the download waits while a file import is running (it does not fail).
  6. Delete the temp file. Outcome `added` → done; `duplicate` (same hash) → done with "Already in your library"; failure → failed with the importer's reason.
- Failures carry a short reason for the row (HTTP status, YouTube's playability reason, "No connection", the importer's reason). Retry re-queues the job at the end.
- On startup, `<temporary dir>/download/` is emptied (best effort, like `cleanupOrphans`). Jobs are not persisted; an app kill loses the queue (acceptable, "keep owntune open").
- Duplicate guard before queuing: if a job for the same `sourceKey` is waiting or running, tapping Download again does nothing; if the library has it, the sheet shows "In Library" (above).

### Rust: write the cover

`write_tags` gains the cover: `TagValues` gets `cover: Option<CoverInput>` with `CoverInput { data: Vec<u8>, mime: String }`, where `None` means "leave the existing pictures unchanged" (Edit Info passes `None`, so its behavior does not change). `Some` replaces all pictures with one front cover. (v0.5.1 will need "remove cover" too; it can extend this then.) Covered by Rust unit tests on an M4A fixture and the DASH M4A from the spike (add a small DASH fixture made with `ffmpeg -f mp4 -movflags dash` in `tool/make_fixtures.sh`).

### Data

- Schema version 2: `tracks.sourceKey TEXT NULL UNIQUE` (`youtube:<videoId>`, later `soundcloud:<id>`). First real migration of the project: `onUpgrade` from 1 → 2 adds the column (drift `m.addColumn`), with a migration test (drift's schema dump + `drift_dev` verifier, or an integration test that opens a v1 file).
- `Importer.importFiles` accepts an optional source key per path (e.g. `importFiles(paths, sourceKeys: {path: key})`) and stores it on insert. Edit Info never touches it. Deleting the track frees the key (re-download possible).
- `TrackRepository.watchSourceKeys()` (or the library snapshot) feeds "In Library".
- Settings: `online_source` (`ytmusic`/`youtube`), `online_recent` (JSON list of up to 10 strings).

### UI notes

- Search Online page: navigation row "‹ Library" + centered "Search Online" + downloads button (when the queue is non-empty); segmented switch; search field (submit runs the search; clear button); results / recent searches / states. Mini player at the bottom like other pushed screens.
- States: loading (spinner below the field), empty ("No results"), error (message + Retry; e.g. "YouTube didn't answer: HTTP 429" or "No connection"), "YouTube changed something" when parsing finds no renderers at all in a 200 response (so a breaking change is recognizable on the iPhone).
- Thumbnails via `Image.network` with `cacheWidth`.
- Download sheet: like the app's other sheets (above the navigator via `MaterialApp.builder` is not needed: it is opened from the page). Cover 120 pt square (rounded), title/artist as headline, source line, grouped fields Title / Artist / Album, Download button. Empty title → Download disabled.
- Downloads sheet: as mockup 10; opened from the downloads button; Done clears finished and failed jobs. When the last job finishes while the sheet is closed, the downloads button shows a check for 3 s, then disappears (if nothing failed); failed jobs keep the button visible (with a warning badge) until the sheet is opened and Done is tapped.

## Testing

- Unit: parsers against recorded, trimmed JSON responses in `test/fixtures/online/` (YouTube Music search, YouTube search, player OK, player LOGIN_REQUIRED, player without itag 140); `guessTags` table; download loop against a fake HTTP layer (chunks, progress, cancel, HTTP 403 mid-file, short read); queue (one at a time, retry, waits for running import, duplicate guard); settings round trip.
- Widget: Search Online page (switch remembered, recent searches, In Library/Downloading tags, error state), Download sheet, Downloads sheet; all with a fake source and fake controller via provider overrides (`pumpApp`).
- Rust: cover write on M4A and DASH M4A.
- Integration (Linux, real Rust): a downloaded-style DASH M4A fixture goes through tag+cover writing and the Importer with a source key.
- **Live test** (`integration_test/online_live_test.dart`): search + resolve + download of one Creative-Commons track against real YouTube. Opt-in via `--dart-define=OWNTUNE_LIVE=true`; skipped in CI (GitHub runner IPs are commonly bot-flagged; a red CI must not mean "YouTube changed"). Run locally before each release.
- iPhone check before the release: search, download, play (also locked), Edit Info on the downloaded song, kill the app mid-download and reopen (no leftovers).

## Risks

- **YouTube breaks the VISIONOS path.** Symptom: player `LOGIN_REQUIRED`/`UNPLAYABLE` or 403 on download. Response: update the client constants (follow yt-dlp's `_DEFAULT_CLIENTS`), release. If no JS-less client remains, the fallback is a TV client plus JS challenge solving (yt-dlp's EJS solver in QuickJS via `rquickjs` in the Rust crate) — a separate decision then.
- **AVPlayer and the `dash`-brand M4A.** Plays in the spike. If a file written by the real pipeline (with tags and cover) ever fails on the iPhone, a Rust remux to a progressive MP4 before tagging is the fix; the iPhone check before the release covers this.
- **Rate limiting / bot checks** on heavy use from one IP; the queue's one-at-a-time rule and search-on-submit keep the request count low.
- **Terms of service.** Downloading from YouTube is against its terms; this is a personal, sideloaded app that is not published in a store (decided by the user).
