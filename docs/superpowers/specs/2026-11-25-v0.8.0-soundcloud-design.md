# SoundCloud in Search Online (design)

Date: 2026-11-25 · Milestone: Downloader (second half) · Release: **v0.8.0** (planned as v0.6.2; renamed because v0.7.3 is installed and a lower version would not show as an update in SideStore)

## Intent

Search Online gets SoundCloud next to YouTube. The user wants it for normal songs that are not on YouTube, or only there in a worse version (remixes, flips, bootlegs, covers by small artists), and **for long DJ mixes** (one to three hours). As with YouTube, a result is downloaded into the library as one file with clean tags and a square cover, through the same queue, the same Download sheet and the same Importer.

Success: on the iPhone, searching "linkin park numb" on the SoundCloud tab, tapping "Linkin Park - Numb (SRY4U FLIP)" and Download puts the song into Library > Songs with its artwork and the right duration, and it plays with the screen locked. A two-hour mix also downloads, plays and can be scrubbed. If the download stops halfway (app sent to the background, network lost), Retry continues where it stopped.

## Decided with the user (2026-11-25)

- Downloads stay **in the app**, YouTube and SoundCloud alike: own small Dart clients, no package. A home server (Raspberry Pi running yt-dlp) comes **later**, only as an optional fallback switch in Settings. Not part of this release, and this release does not design for it beyond keeping the source abstraction clean.
- **Pasting a link** (SoundCloud or YouTube URL) into the search field comes in a follow-up release, for both sources. Not in this one.
- Protected tracks (DRM) and preview-only tracks (Go+) are **shown dimmed** in the results with a note, not hidden: "Protected" or "Preview only". They cannot be opened or downloaded.
- Retry of a failed or cancelled download **continues** from what is already on disk.
- Release name **v0.8.0**.
- Approach: own Dart client against SoundCloud's web API (below). The official API (app registration, secret in a public repo, ToS forbids downloading), a Dart package (none maintained with HLS) and ffmpeg/libmpv for joining segments (Linux only) were rejected.

## What SoundCloud serves today (checked 2026-11-25)

Recon with real requests (see "Recon" at the end for the raw shapes):

- **No progressive MP3 anymore.** SoundCloud removed progressive MP3 and moved to AAC over HLS in 2025/26 ([dev blog](https://developers.soundcloud.com/blog/api-streaming-urls/), [api #441](https://github.com/soundcloud/api/issues/441)). Every track in two sample searches (40 tracks) offered only `hls` transcodings: `aac_160k` (`audio/mp4`), `aac_96k` (`audio/mp4`) and `abr_sq` (`audio/mpegurl`, an adaptive master playlist). Some tracks have **only `aac_96k`**.
- **Label tracks are DRM-protected.** Official uploads (e.g. "Numb" by LINKIN PARK) offer only `cbc-encrypted-hls` / `ctr-encrypted-hls`. These cannot be downloaded. In the "linkin park numb" search, 5 of 20 results were protected, the rest (remixes, covers, slowed versions) were free.
- The media playlist is a VOD HLS playlist (`#EXT-X-VERSION:7`) with one `#EXT-X-MAP` init segment (`init.mp4`) and media segments `data000.m4s`, `data001.m4s`, … of ~10 s each. A 3:09 song has 19 segments; a 2:59:15 mix has 1,076. All segment URLs are signed (query string) and expire.
- Init + all segments concatenated in order give a valid fragmented MP4 (`ftyp iso5`), AAC-LC 44.1 kHz stereo, ~160 kbps. ffprobe reads the right duration (188.848 s for the 19-segment song).
- **lofty reads it with duration 0**: `mvhd` and `mdhd` carry duration 0 (the durations live only in the fragments). lofty writes the MP4 tags into it correctly. After writing the real duration into `mvhd`, `tkhd` and `mdhd` of the init segment (sum of the playlist's `#EXTINF` values, in each box's timescale), lofty reads 188.848 s and ffprobe still reads the file. **Without that patch the Importer would store a duration of 0.** (lofty's bitrate for such a file is wrong, ~8 kbps, but owntune does not store bitrate.)
- The search response already contains, per track: `id`, `title`, `user.username`, `user.avatar_url`, `artwork_url` (may be null), `duration` and `full_duration` (ms), `playback_count`, `genre`, `release_date`, `policy` (`ALLOW`, `MONETIZE`, `SNIP`, `BLOCK`), `publisher_metadata` (`artist`, `album_title`, `release_title`, often missing), `media.transcodings[]` (`url`, `preset`, `snipped`, `format.protocol`, `format.mime_type`), `track_authorization`, `permalink_url`.
- The `client_id` that the API wants is found in the web app's scripts: `https://soundcloud.com/` lists `<script src="https://a-v2.sndcdn.com/assets/….js">`; one of the last ones contains `client_id:"<32 alphanumerics>"`. The same way yt-dlp gets it.

## Goals

### Search Online

- A third tab: **Songs | Videos | SoundCloud** (text tabs, as today). The last used tab is remembered (`online_source` setting gets the value `soundcloud`). The search field label is "Search SoundCloud". Recent searches stay shared across tabs, as today.
- Search = `GET https://api-v2.soundcloud.com/search/tracks?q=<query>&client_id=<id>&limit=20&app_locale=en`. First page only, like YouTube.
- Result rows as in mockup 08 (`docs/mockups/roadmap-v1/08-online-results-soundcloud.html`): square 48 pt artwork with the duration on it (like the video thumbnails), the track title (two lines at most), and below it "uploader · 48K plays". Plays use a compact count: 950, 6.2K, 48K, 2.1M. Same "In Library" / "Downloading NN %" / "Waiting" state as the YouTube rows.
- **Downloadable** = the track has an unencrypted `hls` transcoding with mime type `audio/mp4` and preset `aac_160k` or `aac_96k`, that transcoding is not `snipped`, and `policy` is not `SNIP` or `BLOCK`. Otherwise the row is dimmed, not tappable, and shows a note where "In Library" would go:
  - "Protected": only encrypted transcodings.
  - "Preview only": `policy` `SNIP`, or every usable transcoding is `snipped`.
  - "Not available": `policy` `BLOCK`, or no usable transcoding for another reason.
- Artwork: `artwork_url` with `-large` replaced by `-t300x300` for the row and `-t500x500` for the file's cover (square, no crop). Without `artwork_url`, the same on `user.avatar_url`. Without either, the usual placeholder in the row and no cover in the file.
- `sourceKey` = `soundcloud:<track id>`. "In Library" works through `tracks.source_key` as for YouTube.

### Download sheet

- Same sheet as today. Source line: "From SoundCloud · M4A, 160 kbps" (or "96 kbps" when only `aac_96k` exists; prefer 160 over 96).
- Prefilled tags (the user can still edit Title, Artist, Album):
  - If the title has an "Artist - Title" separator: split it with the same rules as `guessTags` (bracket noise dropped, remix/edit/feat kept).
  - Otherwise Title = the track title (cleaned the same way), Artist = `publisher_metadata.artist` if set, else the uploader's `username`.
  - Album = `publisher_metadata.album_title`, else `publisher_metadata.release_title`, else empty.
  - SoundCloud noise in titles is dropped too: bracket parts like "(FREE DL)", "[FREE DOWNLOAD]", "(Free Download)".
  - A mix keeps its title ("Rainy Sunday Mix #12") with the uploader as artist. No special mix detection.
- Genre (`genre`, if not empty) and year (from `release_date`, if set) go into the tags too, without showing in the sheet. Claude's call, see "Calls made".

### Download

- `resolve` fetches the track again (`GET https://api-v2.soundcloud.com/tracks/<id>?client_id=<id>`), so a job that waited in the queue gets fresh transcodings and a fresh `track_authorization`. It then picks the transcoding (160 before 96), calls `<transcoding url>?client_id=<id>&track_authorization=<auth>`, which answers `{"url": "<m3u8 url>"}`, and fetches and parses that media playlist.
- The resolved stream is now one of two kinds:
  - **One file in range requests** (YouTube, as today: URL, content length).
  - **A segment list** (SoundCloud: init segment URL, media segment URLs with their `#EXTINF` durations, total duration, preset bitrate).
- Downloading a segment list writes the init segment first, **with the total duration patched into `mvhd`, `tkhd` and `mdhd`** (version 0 and version 1 boxes), then every media segment in order, each with a plain GET. The result is `audio.part.m4a` as today, and everything after that (cover, `write_tags`, rename, Importer) is unchanged.
- The duration check: after the download, the file's duration as the Importer reads it must not be 0. Covered by an integration test with a real recorded segment file (below), not by a runtime check.
- Progress in the Downloads sheet: segments done / segment count drives the percentage. The MB line shows bytes received and an estimate of the total (bitrate × duration), e.g. "12.3 of 140.2 MB". For YouTube nothing changes.
- **Retry continues.** The job's folder in `<temp>/owntune-download/` is no longer deleted when a job fails or is cancelled. It is deleted when the job ends as done or duplicate, when Done in the Downloads sheet drops the job (`clearFinished`), and at startup as today. After each fully written segment (SoundCloud) or range chunk (YouTube), the job records how far it got. Retry resolves again (signed URLs expire) and continues from the recorded point if the new stream has the same shape (same segment count and same init segment size for SoundCloud; same content length for YouTube). If the shape differs, it starts over. A partly written last segment or chunk is cut off before continuing.
- Errors name SoundCloud: "SoundCloud didn't answer: HTTP 429", "SoundCloud changed something; owntune needs an update" (a 200 response that does not parse, or no `client_id` found in the scripts), "No connection". Today's `IoHttpTransport` messages say "YouTube"; they must name the service that was asked.
- `client_id`: fetched on first use, kept in `settings_entries` (`soundcloud_client_id`) so not every app start scrapes the web page. On a 401 or 403 from the API, fetch a new one once and repeat the request once.

### Fixtures and tests

- `tool/record_online_fixtures.sh` also records SoundCloud: one search (`test/fixtures/online/soundcloud_search.json`), one track (`soundcloud_track.json`), one transcoding answer (`soundcloud_stream.json`), one media playlist (`soundcloud_playlist.m3u8`), and an excerpt of the home page and of the script with the `client_id` (enough for the extraction test). It scrubs `client_id`, `track_authorization` and every signed query string. The script's header says how many requests it makes.
- A short real SoundCloud init segment + two media segments as an audio fixture (a few hundred KB, a free track) for an integration test: join, patch, `write_tags`, import, and check that the stored duration is right. If a real file is too heavy for the repo, a generated fragmented MP4 (ffmpeg `-movflags frag_keyframe+empty_moov`) with duration 0 in `mvhd` is enough. Builder's call.
- `integration_test/online_live_test.dart` (opt-in, `OWNTUNE_LIVE=true`) also searches SoundCloud, resolves one free result and downloads its init segment and first media segment.
- Unit tests: parsing (downloadable / protected / preview only / not available, 160 vs 96, artwork fallback, tag suggestion), playlist parsing, the duration patch (v0 and v1 boxes), resume (same shape continues, different shape restarts, half-written segment cut off), the `client_id` refresh on 401.

## Non-goals

- Pasting SoundCloud or YouTube links into the search (next release).
- The Raspberry Pi / yt-dlp fallback (a later release).
- SoundCloud sets, albums, playlists, user pages; paging ("load more").
- Login, Go+, protected tracks (no DRM workarounds of any kind).
- Opus or MP3 transcodings; `abr_sq`. Downloading the uploader's original file (`downloadable`) even when offered.
- Tracklists or chapters for mixes.
- Downloads that keep running while iOS has suspended the app (unchanged: "keep owntune open"; Retry now continues instead).

## Anti-goals

- A file that lands in the library with duration 0 or that holds only a 30 s preview.
- Anything secret in the repo: the `client_id` is scraped at runtime, fixtures are scrubbed.
- A SoundCloud change that breaks YouTube downloads, or the other way round.

## Constraints

- No new packages. HLS parsing, joining and the box patch are a few hundred lines of Dart; the file then goes through the existing Rust `write_tags` and Importer.
- Every SoundCloud host, path, query parameter and the `client_id` pattern live in one file (like `innertube_clients.dart`), so a SoundCloud change is fixed in one place.
- iOS: **checked on the iPhone on 2026-11-25** with two hand-made files built exactly as specified here (plain concatenation of init + segments, duration patched into `mvhd`/`tkhd`/`mdhd`, tags written by lofty), imported through Import Music: a 3:09 song and a 57:25 mix (345 segments, 70 MB) both show the right duration, play, and scrub (also from the lock screen). So the plain join is enough; no rewriting of the file layout. The usual iOS check of the real download before the release still applies.

## Left to the builder

- How the two stream kinds are modelled (sealed class or similar), and how `OnlineResult` carries the SoundCloud id (today's field is called `videoId`; renaming it is fine).
- How the transport learns the service name for its error messages.
- How many segments are fetched at once (one by one is fine; a few in parallel, e.g. 4, keeps a 1,000-segment mix from taking much longer than needed, as long as they are written in order).
- The format of the job's progress record.
- The fixture for the duration test (real excerpt or generated).

## Calls made (Claude's, not discussed)

- Genre and year are taken from SoundCloud without showing in the sheet. SoundCloud genres are free text ("Deep House", "techno", sometimes junk); the Stats Genres card would show them. Easy to drop if unwanted.
- YouTube downloads also resume on Retry (same mechanism, nearly free with range requests).
- Rows that cannot be downloaded are not tappable at all (no sheet, no explanation beyond the note).
- `client_id` is cached in the settings table.
- Artwork 500 px for the file (SoundCloud's largest regular size; the `original` size can be huge).
